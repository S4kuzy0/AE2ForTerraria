三、目标架构：沿现有模块收拢规则

先画出本轮会修改的真实调用链，再实施最小必要拆分。保留以下主体，不进行全库搬家或引入大型框架：

• Core/ItemKey.cs、ItemPersistence.cs、SavedItemGuard.cs：身份、实际物品数据及保存恢复的唯一入口；不能为性能省掉自定义数据比较。
• Core/StorageLedger.cs、StorageTransaction.cs：数量、容量、私有账本预演与提交。保留产物容量不足时不扣原料的保护。箱子、光标、磁盘槽等跨容器操作要明确自己的原子边界，不能把账本事务等同于所有游戏操作都已原子化。
• Systems/StorageOperations.cs 及少量共用操作方法：负责存取、换盘和升级等业务规则。单人和服务端调用同一规则；UI 和网络接收器只转换意图及展示结果。需要时提取一个小型操作结果，携带实际完成量、余量、失败原因和需同步的对象。
• Systems/MENetwork.cs、NetworkInventory.cs、NetworkRegistry*.cs：分别负责连接组件、带版本的库存汇总、权限及拓扑策略。共享拓扑快照，避免同一操作多次遍历；拓扑变化必须同时使库存、权限、订阅及活动任务的相关状态失效。
• Core/RecipeIndex.cs、CraftPlanning.cs、RecipeExecutionPolicy.cs，Content/Tiles/MECraftingCpuEntity.cs、MEMolecularAssemblerEntity.cs：分别负责候选配方、计划、可执行性限制、持久任务及执行调度。预览与执行共享数量和条件语义，执行前重新核验库存与权限。保留稳定任务标识、暂停/取消保护和逐批提交前重规划。
• Systems/GameDataIndex.cs、NpcIndex.cs、Core/RecipeIndex.cs：提供当前加载内容的查询数据；UI/UIBrowserDetails.cs 等只管理选择、分页、历史和绘制。把需要共享的掉落条件、数量及概率保留为结构化数据，到显示时再生成文字。
• Systems/MENet.*.cs：校验发起者、实体、范围、权限、数量和请求状态，服务端决定结果，客户端应用完整且有明确有效期的状态。不能接受客户端上传账本或容器快照作为事实。

允许核心代码使用 Terraria API；依赖方向的重点是业务规则不依赖窗口状态。Core/ItemSearch.cs 当前直接依赖 UIItemNames：若本轮统一搜索，顺带把名称/模组元数据查询移到内容查询侧，不要仅为消除一个 using 增加接口体系。

四、源码已经证实的工作清单

A. 无 CPU 的新增合成订单被已有成品抵消——首批核心修复。
入口：UI/TerminalUIState.cs:814、Systems/MENet.Server.cs:118 设置装配室 Target。
原因：Content/Tiles/MEMolecularAssemblerEntity.cs:468 调用 Plan 时沿用 useExistingTarget=true；已有目标物时在 :481 清空 Target。CPU 分支 :430 已明确传 false，UI/UIRecipePanel.cs:230 的制作预览也采用新增制作语义。
验收：无 CPU、已有成品、材料充足，从单人和多人下单入口新增制作；旧成品保留，扣除对应材料，新增正确批次。区分“新增制作”和“保持库存”，不要修改规划器默认参数后让保持库存语义退化。同时检查批量产出、空间不足和重进后的目标恢复。

B. 原版箱子只有部分接触方位能被总线识别——首批核心修复。
原因：Content/Tiles/MEStorageBusEntity.cs:130 与 :203 都把相邻方块坐标直接交给 Chest.FindChest。安装目录 tModLoader.xml:478 明确要求箱子左上角坐标。
验收：遍历原版箱子的合法周边接触格，自动导入、自动导出和手动全网导出识别一致。抽出共用解析，确认接触箱子子格后再定位左上角并去重，不能扩大半径导致隔墙或远距误连。覆盖空箱、满箱、部分容纳、过滤、物品锁和箱子移除；逐槽核对数量与身份。

C. 多人升级存储单元后，等级与手持升级件缺少同步——首批核心修复。
原因：Systems/MENet.Server.cs:164 在 TryUpgrade、扣除 HeldItem 后只广播账本。Content/Tiles/MEStorageUnitEntity.cs:28 的 Level 没有相应网络序列化，UI/StorageUnitUIState.cs:178 又按旧 Level/CurrentCapacity 显示。
验收：发起者、旁观者、离开后重连的客户端看到同一等级和容量；升级件只消耗一次，失败不消耗。既覆盖按钮入口，也覆盖方块右键入口，覆盖满级和无权限请求。不能因为显示不同步就宣称已经证明可复制升级件。

D. 可行合成因原料竞争被误判缺料——规划修复。
原因：Core/CraftPlanning.cs:129 按原料顺序递归，:138 遇到局部零缺料方案立即选定；后续原料失败不会回溯前一原料的路线。:148 的配方组现货消耗也按类型顺序直接取用。
反例：成品需要部件甲和部件乙；甲可由木材或石块制造，乙只能由木材制造；库存木材、石块各一份。甲先选木材路线就会错误缺料，选择石块路线则可行。
验收：上述多配方竞争、配方组与严格原料竞争、调换配方/材料登记顺序、混用替代材料、中间产物余量、循环、批量产出均有明确结果。使用有预算的局部回溯或等价的有限搜索；给出预算耗尽状态，不能把未找到方案直接说成必然缺料，也不能令复杂配方卡住主线程。无须求成本最优的通用解。

E. 同网络的第二个 CPU 可能长期不被调度——调度修复。
原因：Systems/MENetwork.cs:306 的 FindEntity 返回首个实体；FindCraftingCpu 沿用它。装配室 :394 只检查这个 CPU，首个暂停、缺料或没有工作时都不继续寻找其他 CPU 的可执行任务。
验收：两套有队列的网络合并；首个 CPU 分别为空、暂停、缺料，后面的 CPU 有可执行任务。后者应推进，原队列状态保留；多个装配室不能对同一剩余量重复结算。候选扫描必须有稳定顺序及合理开销，暂停一个 CPU 不应暂停全网其他 CPU。
选中任务后，完成、取消、暂停、断开及周期同步都必须沿用真实所属 CPU。检查装配室 Update :280 与 ClearActive :320，它们目前会重新调用 FindCraftingCpu 找首个 CPU；仅修改候选扫描会遗留清理和同步错误。验收非首个 CPU 的活动标记与客户端进度正确更新、清理。

F. 单人换大盘与多人规则不一致——交互预览确认后修复。
原因：UI/DriveUIState.cs:83 的 CanRemoveDisk 和 UI/UIItemSlotElement.cs:166 先按“只拔旧盘”拒绝交换；Content/Tiles/MEDiskDriveEntity.cs:132 没计入新盘容量。多人 Systems/MENet.Operations.cs:64、:74 则按替换后盘组校验。
验收：旧盘承载库存时，容量足够的大盘或同级盘可以直接交换；容量不足时盘、鼠标物品和账本均不变。覆盖左键交换、右键单件操作、所有盘位已满和两端并发请求。共用操作规则，不再保留两套容量判断。

G. 异主无线网络意外合并后，频道按钮无法解除连接——安全恢复流程。
原因：Systems/NetworkRegistry.cs:143 对原始策略取最低权限；双方未相互授权时都失权。Systems/MENet.cs:192 又要求整网管理权限才能改频道，Server.cs:27 在 :237 的改频道逻辑前就拒绝。
边界：可以通过拆桥或断线恢复，不是永久损坏存档。不要放松合并后库存权限来换取方便。
验收：建立不同所有者网络并切到同一频道，通过安全、范围受限的恢复连接操作恢复独立状态；其他玩家不能借机改频道或获取库存。若增加或调整交互，先做预览。现有 TopologyChecks 直接调用 TrackComponent，不能替代实际服务端请求入口验证。
不得直接豁免 ClientCycleBridge 的权限检查，也不得把任一原所有者视为合并网络管理员。恢复授权依据合并前保留的原组件策略，限定到本人有权管理的桥；核验变更后的连接关系，防止借恢复操作接入第三方网络。分别覆盖本人恢复、他人操作及切入第三方已占用频道。

H. 失去读取权限后，远程终端保留旧库存并重复请求——状态一致性修复。
原因：Systems/MENet.Client.cs:128 的 ServerDenied 只清光标等待并提示；Systems/UISystem.cs:513 继续使用缓存，:863 在终端打开期间继续请求。
验收：撤销读取权限、网络失效、频道变化时，缓存与可操作状态明确失效，停止无效重试；恢复权限后能重新获取。区分单次写操作被拒与整个网络不可读，不要任何拒绝都清空所有窗口。旧数据仍显示不等于服务器继续泄露新库存或允许越权取出。可见的失权状态先预览确认。

I. 用途/NPC 页面会污染之后的配方导航——浏览器交互修复。
原因：UI/UIBrowserDetails.cs:76 的 Show 只在 uses=true 时设置用途标签，false 不切回配方；ShowNpc 又把标签置为来源。UI/UIItemGrid.cs:450 的 U 和 :454 的 R 经 SearchUIState.Activate 进入同一 Show。
验收：先查用途，再按 R 查询另一物品，必须进入它的配方；先查 NPC 再查询物品同样正确。区分“明确打开配方”“打开用途”“恢复历史页面”“后台刷新”，不能粗暴每次重置标签损坏前进/后退与刷新。独立预览验证切换不闪、不重复播放入场、不重排网格，再接入运行代码。

J. 掉落查询的数据模型丢失条件，零概率被映射成必掉——来源数据及展示修复。
原因：Systems/GameDataIndex.cs:195 将非正 dropRate 改为百分之百，:205、:213 的索引和来源文字丢弃条件及数量区间；同文件容器掉落 :649 有相同概率处理。CollectDrops 没过滤这些条目。UI/UIBrowserDetails.cs:230 使用这些来源，而 :240 的 NPC 页面另行直接读取规则，因此两处数据精度不一致。
边界：错误转换分支和条件丢失已由源码证实；当前模组包具体哪些条目出现零概率，仍需枚举实际数据证明。
验收：条件掉落、零概率、未知/异常规则、数量范围、同物品多条规则均准确处理；保留各自条件，不能简单相加成超过上限的概率。物品来源与 NPC 掉落共用同一查询数据，能互相导航。用受控数据验证，另抽查真实模组条目。将完整来源信息和可点击条件说明作为此阶段的用户收益，先预览其展示方式。

五、风险验证：取得证据后才决定是否修改

• 鼠标槽跨原版同步与 ME 请求的竞态：Systems/MENet.Operations.cs:27 先同步鼠标槽再发操作，MENet.Client.cs:145 的响应覆盖 Main.mouseItem。测试等待期间关窗、移动原版背包物品、断线、重复操作及迟到响应；追踪槽位序号、请求身份和总量。目前没有端到端复制或丢失证据，不把风险写成既成事故。
• 总线导出异常原子性：MEStorageBusEntity.cs:314 先扣账再 FillChest。受控注入物品重建失败、部分填入后失败，核对两端总量与自定义数据。若不能回滚，改成先准备完整槽位结果，再一次提交；不能吞异常当成功。
• GlobalItem.OnCreated：RecipeExecutionPolicy.cs:19 检查配方回调及 ModItem.OnCreated，没有处理全局创建钩子；StorageTransaction 直接入账。用受控钩子验证自定义产物标记，再查实际启用模组是否受影响。按受影响物品处理，不能检测到任意全局钩子就禁掉全部自动合成。
• 合成条件上下文：查 CanUseRecipe 的 Condition.IsMet 在服务端、请求玩家、装配室位置、昼夜/液体/群落下的含义；预览与实际提交须一致。不要仅因方法返回 true 就认定是正确玩家上下文。
• 任务执行中撤权或网络合并：ProduceOne 目前只为锁定原料检查管理权限，普通任务没有一般使用权限复核。先明确手工订单与保持库存的授权归属，再验证提交及向玩家投递时的权限；离线、撤权、取消、合并不能混作一种状态。
• StorageOperations.Withdraw 的 ground 参数和提示是否相符：当前无论是否指定落地均创建地面物品，而提示包含“空间不足时余量仍在网络”。完整追踪拾取、背包容量、掉落槽失败及 CPU 投递，再决定是否收拢行为；不能仅看名字认定已安全进入背包。
• 联机分片、拓扑变化、世界切换、模组重载及长时间运行：测试缺片/重复/过期响应、断线后缓存清理、旧网络快照晚到；列出每种缓存的内容、键、失效事件和持有期。已有 WireChecks 主要测试账本编解码，未证明这些状态转换。

六、性能工作只针对能测量的热点

首选测量总线空转导出：MEStorageBusEntity.cs:274 每轮复制账本，:365 为每个候选物品遍历箱格并调用 ItemKey.FromItem，连已满或类型不符的格子也先算身份。ItemPersistence.cs:84 会序列化实际物品及默认物品。重复工作已证实，实际卡顿程度尚未测量。

记录代表性库存规模、总线数量、单次/连续扫描耗时、分配量、身份序列化次数及总线实际搬运量。优先先判类型/词缀/空间，并在一次扫描内复用槽位身份；自定义物品状态可变，不能仅用类型和数量作为跨周期缓存依据。不要把静默跳过扫描当性能优化。

另测 Core/ItemSearch.cs 每个物品重复 Split 查询词、目录重复排序和配方工作站反查。确有收益时把查询编译为一次可复用的词项，缓存按查询/排序/库存版本失效。保持中文、拼音、词缀、排除词和精确模组选择语义。报告测量条件与前后数据，没有测量不写提速比例。

七、分阶段实际交付

阶段一：备份与反例，完成 A、B、C 的共用逻辑修复；先验证高风险操作的数量与身份守恒。阶段内若发现更严重且可复现的数据破坏或越权问题，记录证据后优先解决。形成一个范围清楚、能独立回退的核心版本。

阶段二：完成 D、E 与经验证需要修复的执行兼容/权限问题；复用现有账本事务和任务模型，验证规划、调度、提交一致。给出有预算搜索的行为界限，并测量相关热点。

阶段三：先预览 F、G、H、I、J 中涉及的交互，再按确认范围实现；补齐来源查询可靠性与状态反馈。保留已批准的外观和操作习惯，把缺失功能按 Recipe Browser 对照表逐项推进。不要为了凑数量增加空入口；本阶段完整完成选定功能后再扩大范围。

每阶段先给简短、对应文件与调用链的实施方案，然后继续执行。逐项状态使用“待复现、已复现、已修复、已验证、受限未验证”，保留最小反例、断言、日志和对应源码版本。新 UI 待确认时可以继续独立核心任务，不能擅自将未确认方案混入安装包。不要每修一处就询问是否继续。

八、验证、构建与安装

扩展 Systems/RegressionChecks.cs 和 UiRegressionSystem.cs 中有价值的断言；入口/状态转换问题必须走真实业务入口，不能只反射注入最终状态。关键失败路径要验证修复前失败、修复后通过。测试不得给正常游戏增加常驻开销，也不能修改用户内容。

现有环境开关为 AE2_RUN_REGRESSION=1 和 AE2_UI_REGRESSION=1。仅为测试子进程设置，结束恢复；不要持久修改系统环境。检查日志中的 COMPLETE、FAILED 和异常，RegressionChecks 会捕获异常写日志，进程正常退出本身不是测试通过证据。

客户端启动前先告知用户。UI 至少做静态布局/贴图检查；针对输入、闪烁、遮挡和拖动问题，尽可能走真实 UserInterface 更新与鼠标按下/释放路径，并明确哪些只做了菜单渲染。覆盖已支持的小窗口、常用分辨率、缩放、中文长名称、输入法、滚动和叠窗；不要用服务端加载代替 UI 验证。

多人修改使用实际启用模组的服务端与客户端核验；双客户端无法完成时如实保留该限制，不宣称单人回归证明多人正确。世界/角色验证只使用隔离的测试对象，保护原有存档。
客户端必须实际连接隔离测试世界、执行请求并比对两端状态；同时启动进程或各自加载到菜单不算联机验收。下方的 -server -autoshutdown 仅用于加载检查，不能代替真实连接与操作验证。

每个完成版本递增 AE2ForTerraria\build.txt 的 version，并立即构建安装到默认存档目录。确认 UI 授权满足后，从 tModLoader 安装目录执行以下 PowerShell；-build 必须传完整源码路径：

$tl = 'D:\SteamLibrary\steamapps\common\tModLoader'
$proj = 'C:\Users\ROG\Documents\ChatGPT\ae2 for tr\AE2ForTerraria'
$sd = 'C:\Users\ROG\Documents\My Games\Terraria\tModLoader'
Set-Location -LiteralPath $tl
& "$tl\dotnet\dotnet.exe" "$tl\tModLoader.dll" -build $proj -tmlsavedirectory $sd -nosteam

核对本次构建没有错误，安装包版本、大小、写入时间及 SHA256 都对应新产物。绝不安装到 calamity-pro\SaveData。检查源码目录 Junction 指向，避免维护两份源码。

服务端加载验证命令如下，不能添加 -nosteam，否则跳过创意工坊内容：

& "$tl\dotnet\dotnet.exe" "$tl\tModLoader.dll" -server -tmlsavedirectory $sd -autoshutdown

日志位于 tModLoader-Logs\server.log 和 client.log。服务端会跳过纯客户端模组，不能用旧的固定数量作为全部环境验证成功的标准。游戏已运行时不擅自强杀用户会话，告知新版本需要重启加载；启动新的客户端前履行告知。

最终交付必须包含：落实的模块边界；每个问题的触发条件、修复和验证证据；获批 UI/可用功能的改变；版本、安装绝对路径与哈希；存档保护检查；未验证内容和剩余问题。用中文简明说明，附可点击文件链接。只有审查、预览、编译或旧报告时，分别如实标注，不能宣称已完成游戏验证。
