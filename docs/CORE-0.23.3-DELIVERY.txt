已落实的模块边界
物品身份继续由 Core/ItemKey.cs、ItemPersistence.cs、SavedItemGuard.cs 负责，保存格式保持兼容。存储数量与容量继续由 StorageLedger/StorageTransaction 负责。UI 的升级按钮和方块右键转为调用 StorageOperations.TryUpgradeStorageUnit；界面不直接承担权威扣除。
单格、同类和批量存入统一经 MENet.Deposits：客户端提交操作意图、候选槽和身份摘要；服务端按自身背包数量、权限及容量执行 StorageOperations.DepositInventory，再发送原版槽快照与对应完成序号。摘要只用于检测槽变化，实际入库仍使用完整 ItemKey 自定义数据。升级沿同样的等待/确认原则同步等级与容量。
RecipeIndex 仍提供配方候选；CraftPlanning 保留常见成功路线，失败后进行有限回溯。CPU 持久化队列，装配室管理当前真实所属 CPU、分次候选扫描及逐批提交前的计划、权限、任务和存储连接复核。未引入框架或重写存档。
总线将原版箱子接触格归一到左上角，导入、导出和手动操作共用解析。导出先准备所有需要重建/克隆的槽结果，确认身份和源版本后再提交扣账与箱格；一次扫描的身份缓存在成功或失败后失效，不跨周期复用可变自定义数据。

已修复与证据
A：无 CPU、已有成品时新增订单会被库存抵消。仅新增制作传 useExistingTarget:false，保持库存语义不改。单人终端入口、解码请求、目标存取档、输出满容量/恢复均有实际 API 回归；真实 TCP 火把订单保留原有五个火把并增加三件，木材和胶各消耗一件，两端及重连库存一致。
B：总线直接把箱子子格交给 Chest.FindChest，部分接触面无法识别。现在先确认相邻原版容器并解析原点、去重，未扩大连接半径。实际 Update 和公共手动导出覆盖周边接触、梳妆台、过滤、锁、容量、前缀及箱子移除。
C：升级等级/容量和升级件缺乏完整多人确认。共用升级操作、服务端元数据与带序号的完成回包；等待期间保护参与槽。真实两个客户端检查原槽扣除、切快捷栏、只读拒绝、满级拒绝、旁观者容量及重连。测试调用按钮/右键共用的公开业务入口，不宣称物理鼠标点击过两个入口。
背包存入：实际原版收包路径复现了本机旧栈残留，并可再次入账。新增候选槽锁、权威快照和完成序号，旧无确认协议停用；回归检查容量不足、部分成功、重放、截断、身份变化与清理。真实 TCP 覆盖单格、同类、普通批量、含钱币弹药、收藏保护和只读拒绝。强制断线发生在服务端提交与本机保存之间的跨存档原子性仍未保证。
D：局部贪心路线抢占后续必需材料。失败后回溯先前配方与配方组分配，验证登记顺序、混合替代材料、批量、中间余料和循环；未穷尽的搜索保留 Limited，优先使用既有复杂度提示。搜索设步骤和深度边界，不求全局成本最优。
E：只检查首个 CPU 导致其他队列停滞，且清理/同步可能找错 CPU。现在稳定排序并轮转候选，保留真实所属 CPU，支持分次继续扫描；不因普通库存变化抹掉扫描进度。实际 Update 验证首队列空/暂停/缺料、多装配室剩余量与批量结算、活动标记、取消、断开/替换与恢复。
执行权限与状态：命名手工订单在选择及提交时重新验证使用权限。条件回调撤权、取消、暂停、拆 CPU、拆存储或替换实体时拒绝旧计划提交；恢复后正常执行。匿名保持库存和旧匿名目标保留兼容行为，不能视作具有完整发起者审计。
总线异常：实际修复前服务端回归证明，重建失败可让原有 \(3\) 件库存变为 \(0\)。修复后导出先准备、再提交，异常保留源和目标；导出坏条目不阻塞后续正常条目。自定义数据突变、回调失败、较小实际堆叠上限和再次扫描均有回归。
入服状态包：早期 SyncPlayer 在玩家尚未 active 时提前返回，触发正常包未读尽的日志。现在先完整解码最多五个绑定，再验证身份和权限，截断不发布部分状态；没有对所有未知包进行全局跳读。
